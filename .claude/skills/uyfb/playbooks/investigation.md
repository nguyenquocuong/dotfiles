# Investigation

**You own the answer.**
The task is read-only.
It ends in a cited explanation or a recommendation, not a code change.

1. Read the code that answers the question.
   For "why is it like this", read the git history (`git log -S`, `git blame`) and the project's design records (ADRs, specs).
2. Check claims by running something when you can: a test, a small script, the CLI.
   An answer from running beats an answer from reading.
3. Write the answer in this shape:
   overview, key concepts, how it works, where things live (`file:line`), and gotchas.
   For "should we do X or Y", write a recommendation with a tradeoffs table instead.
4. Label each claim as verified, inferred, or not checked.

No code changes.
If the answer leads to a change, say so and switch to Bug fix or Feature in a new todo list.

**Reply.** The answer.
For "are we sure?", give your real judgment with reasons.
If the premise of the question is wrong, say so.
